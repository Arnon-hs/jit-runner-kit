# Governance

`jit-runner-kit` currently uses a lightweight maintainer-led model appropriate for a pre-1.0 project with one maintainer.

## Decisions

- Documentation and focused bug fixes may be approved directly by a maintainer.
- Features and new provider drivers should begin with a public issue or discussion.
- Breaking API, security-boundary, or governance changes require a written proposal and a reasonable public comment period.
- The project lead makes the final decision when consensus is not reached and records the reasoning publicly.

## Roles

- **Contributors** submit issues, discussions, documentation, tests, and code.
- **Maintainers** triage work, review changes, manage releases, and handle security reports.
- **Project lead** is the final decision maker and appoints or removes maintainers.

Current ownership and the path to maintainership are documented in [MAINTAINERS.md](MAINTAINERS.md).

## Transparency

Technical decisions should happen in GitHub issues, discussions, or pull requests. Private channels are reserved for vulnerabilities, conduct reports, credentials, and personal information.

## Changes to governance

Governance changes require a public pull request. Until there are multiple active maintainers, the project lead approves them. If the maintainer group grows, this document should be revised toward shared approval rules.
